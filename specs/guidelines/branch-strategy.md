# ブランチ戦略・リリース運用ガイドライン（`branch-strategy.md`）

本ドキュメントは、Git ブランチ戦略および `pub.dev` へのリリース運用・品質ゲートを規定する。
原則は **【 安全性 ＞ シンプルさ（KISS） 】** とし、不変なパッケージリリースのトレーサビリティを最小限の運用コストで担保する。

---

## 1. 基本方針 & 共通ルール

1. **`main` 1 本化（GitHub Flow 拡張型）**:
   - `main` を唯一の安定ブランチ（常にテスト全パス・リリース可能状態）とする。`develop` ブランチは設けない。
2. **直接コミット禁止**: すべての変更は目的別の作業ブランチから行う。
3. **マージはすべて `--no-ff` 必須**: 履歴可視化とリリーストレーサビリティのため、例外なくマージコミットを残す（Fast-forward 禁止）。
4. **ブランチの破棄**: マージ完了後、作業ブランチは速やかに削除する。

---

## 2. ブランチ体系

| ブランチ種別 | 命名規則 | 主な用途 |
| :--- | :--- | :--- |
| **Main** | `main` | リリース可能安定ブランチ（保護対象） |
| **Feature** | `feature/<name>` | 新機能の実装 |
| **Fix** | `fix/<name>` | バグ修正 |
| **Docs** | `docs/<name>` | ドキュメント・内部仕様書の更新 |
| **Chore** | `chore/<name>` | CI/CD 設定・依存関係調整・雑務 |
| **Release** | `release/vX.Y.Z` | バージョンアップ・公開準備専用（コード変更不可） |
| **Hotfix** | `hotfix/vX.Y.Z` | 公開済みバージョンへの本番緊急パッチ |

---

## 3. 日常の開発サイクル

1. **作成**: 最新の `main` から作業ブランチを作成。
2. **実装**: 標準開発サイクル（ドキュメント → テスト → コード）に沿って Conventional Commits 形式でコミット。
3. **品質ゲート（マージ前必須）**:
   - `fvm flutter test`: 全テスト合格
   - `fvm dart analyze`: 警告・エラー 0 件
4. **統合**: `main` へマージし、作業ブランチを削除。

---

## 4. リリース運用フロー（pub.dev 公開）

新バージョンの公開（および緊急パッチ）は、以下のプロトコルに従う。

1. **準備ブランチの作成**:
   - `release/vX.Y.Z`（緊急時は `hotfix/vX.Y.Z`）を作成。
   - `pubspec.yaml` の `version` 更新および `CHANGELOG.md` へのリリースノート追記のみを行う。
2. **公開前必須検証ゲート**:
   - `fvm flutter test`: 全テスト合格
   - `fvm dart pub publish --dry-run`: **警告 0 件（完全ゼロ）** の確認
3. **統合 & タグ付け**:
   - `main` へマージ。
   - マージコミットに Git タグ（`vX.Y.Z`）を付与し、リモートへプッシュ（`--tags`）。
4. **公開 & 完了**:
   - CI/CD（Trusted Publishing）または手動（`fvm dart pub publish`）で公開を確認。
   - 準備ブランチを削除。
